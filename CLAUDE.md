# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project goal

An IntelliJ Platform plugin (Kotlin) that lets users work with [Cucumber.js](https://github.com/cucumber/cucumber-js) projects: Gherkin `.feature` files whose steps are implemented in JavaScript/TypeScript step definition files.

## Project state

v1 is in progress: run and debug a feature, scenario or Scenario Outline example row from the gutter of `.feature` files, with results in the IDE test runner, and navigate from steps to their step definitions. Planned work and known bugs are in `BACKLOG.md`, with IDs like `B1` or `F2`. When you finish an item, check it off there (`[x]`) and leave it in place. `verifyPlugin` rejects the template's default `<vendor>` values, so keep a real vendor in `plugin.xml`.

The run feature lives in `src/main/kotlin/run/` (package `com.wulfindustries.plugins.run`). It is built on three plugin dependencies:
- JetBrains' **Gherkin** plugin (Marketplace, pinned in `build.gradle.kts`) for `.feature` PSI.
- The bundled **JavaScript** and **NodeJS** plugins for Node interpreters, process launching and the Node debugger. The run configuration extends `AbstractNodeTargetRunProfile` and the state implements `NodeBaseRunProfileState`, following the shape of JetBrains' Mocha integration.

The plugin runs the project's own `@cucumber/cucumber` with `--format message` as the last argument, so the NDJSON goes to stdout alongside the steps' own output, in the order things happened. `CucumberJsTestEventsConverter` (registered through `SMCustomMessagesParsing` on the console properties) picks the messages out of stdout. `CucumberMessagesTranslator` turns them into TeamCity service messages for an id-based tree (`isIdBasedTestTree` on the console properties, so every message carries `nodeId`/`parentNodeId`). At the first `testCaseStarted` it registers the whole tree as pending (`running='false'`), built from `testCase` messages, not pickles, because cucumber-js emits a pickle for every scenario it parses, including filtered-out ones. `GherkinIndex` maps AST ids to rules, outlines, Examples tables, backgrounds and step keywords. The tree is Feature > Rule > Scenario > Background > steps, or Feature > Rule > Outline > Examples (only with several tables) > row > Background > steps. Steps are the tests. Rows are named `Example #k`, their 1-based position in their Examples table, as in the breadcrumbs and the Scenario Inspector. Hooks only get a node when they do not pass. Retries add `Attempt N` suites. A failure in an attempt that will be retried is reported as ignored, so it doesn't turn the scenario red. Anything never started is ignored as "Not run" at `testRunFinished`, because the runner marks the whole tree terminated otherwise. The translator also fills the run's `ScenarioCounts` (held by `CucumberJsTestConsoleProperties`, one per run), which counts scenarios (an outline once, finished with its last row) and pickles (each example row is one), e.g. `Scenarios: 4 of 4 · Pickles: 4 of 7 · 4 left`. The rows of an outline share a scenario key, the pickle's first AST node id. `ScenarioCountLabel` shows them in a label of its own in the free center of the status line above the console, because the platform redraws its "Tests passed" text on every event. Events are routed by `testCaseStartedId`, since `--parallel` interleaves test cases. Other process output is wrapped as `testStdOut`/`testStdErr` for the running step while exactly one test case runs; otherwise it passes through. The process runs without a PTY because ConPTY can wrap long NDJSON lines. Test locations are `file://<path>:<line>` URLs built by `CucumberJsLocations`. Use that helper everywhere so gutter state icons match the test tree. Outline steps under a row point at the row as `:<row line>:1`; the column keeps their URL apart from the row's, since the IDE stores one gutter state per URL.

"Rerun Failed Tests" (`CucumberJsRerunFailedTestsAction`) reruns whole scenarios / example rows, which the translator tags with `metainfo="scenario"`. Because the tree's lines go stale once a feature file is edited, `ScenarioAnchors` puts a `ScenarioAnchor` on every tagged node when the first scenario starts: a `RangeMarker` on the scenario keyword or row, plus a name-based `ScenarioPath` (rule, name, occurrence, Examples index, cells) as a fallback for when the marker is invalidated. Run configurations created from the gutter store that `ScenarioPath` next to their line. The producer leaves `sourceElement` as the clicked element: the platform ranks configurations by source element (a descendant beats its ancestor) before `shouldReplace`, and Cucumber for Java, which accepts every feature file, keeps the clicked leaf. Every feature file belongs to exactly one runner, by where it sits (`CucumberJsTargets.isCucumberJsFeature`): walking up from it, a `package.json` declaring `@cucumber/cucumber` or a `node_modules/@cucumber/cucumber` install makes it ours, a JVM build file (`pom.xml`, `build.gradle(.kts)`) makes it not; with neither it's ours. The answer is cached per directory, because Gherkin calls `supportsStep` for every step × step definition. This covers workspaces that hoist `node_modules` above a sibling Java module. For files that aren't ours the producer creates nothing, the line marker contributor leaves Gherkin's own icons, and `CucumberJsStepDefinition.supportsStep` keeps JS definitions from resolving, so a step text defined in both languages is never ambiguous. For files that are ours, `shouldReplace` wins over other runners (directories keep both). Whether Java definitions resolve from JS features is up to Cucumber for Java, which scopes by module. `CucumberJsRunConfiguration.currentLocation()` looks the scenario up again on every run, so plain Rerun and saved configurations also follow edits.

A directory with a `.feature` file anywhere below it (`CucumberJsTargets.containsFeatures`, through the file type index) can be run from its Project view context menu by the same producer. Its configuration's `featurePath` is the directory and `line` is `null`; cucumber-js runs every feature file below a directory path.

Step navigation lives in `src/main/kotlin/steps/` (package `com.wulfindustries.plugins.steps`). `CucumberJsExtension` implements the Gherkin plugin's public `cucumberJvmExtensionPoint`. That one extension gives Ctrl+click from steps, completion, and Gherkin's undefined-step inspection, whose "Create step definition" fixes call `CucumberJsStepDefinitionCreator` (stubs come from `CucumberJsSnippet`). `CucumberJsSupportCode` finds `Given/When/Then/defineStep/defineParameterType` calls with literal arguments in project JS/TS files outside `node_modules`. It finds candidate files through the word index by those identifiers, because the index doesn't hold string literals like `'@cucumber/cucumber'`. The result is cached project-wide until JS/TS PSI changes (`PsiModificationTracker.forLanguages`), so editing feature files doesn't rescan it. Strings are always Cucumber expressions in cucumber-js; only regex literals are regexes. Gherkin matches with `Matcher.find()`, which is how cucumber-js handles an unanchored regex.

Examples table helpers and the Scenario Inspector live in `src/main/kotlin/tables/` (package `com.wulfindustries.plugins.tables`): rainbow columns (`RainbowColumnsAnnotator`), the column at the caret highlighted in every row (`CurrentColumnHighlighter`, an `EditorFactoryListener`), breadcrumbs for `.feature` files (`GherkinBreadcrumbsProvider`), and the Scenario Inspector tool window (`ScenarioInspectorToolWindow.kt`). The tool window has two tabs, Scenario (first, selected) and Example Values, that share one `ScenarioSelection`. Its `target` is what the gutter's Run would run at the caret (`CucumberJsTargets.exampleRow`, else `runnableScenario`): an Examples data row, or a Scenario, or a Scenario Outline away from its rows. `row` is the target only when it is a row. It follows the caret in `.feature` files and the scenarios and rows that get run (`ExecutionManager.EXECUTION_TOPIC`, resolved through the run configuration's `ScenarioPath`). It is empty on a Feature, Rule or Background, or when something bigger than one scenario runs. The Example Values tab only shows rows. It compares the row with a pinned one (one pin per Scenario Outline) and edits values. It only moves the editor caret when the user selects a line while "Jump to cell on selection" is on. The Scenario tab (`ExpandedScenarioPanel`, text from `ExpandedScenario`) shows Backgrounds plus the scenario, under a `Feature:` line (without one Gherkin parses no steps). For a row, the outline's placeholders are replaced; for an outline target they stay as written. Its viewer is backed by a `LightVirtualFile` whose PSI is created before any text is set, since PSI created later parses the file's empty content instead of the document. `ExpandedScenarioPanel.linkTo` makes its steps resolve as if they were in the scenario's file: the PSI's `FileContextUtil.INJECTED_IN_ELEMENT` gives Gherkin a module, and the light file's `originalFile` gives `CucumberJsTargets.isCucumberJsFeature` a location. `linkTo` creates a smart pointer, so it must run in a read action. `ExpandedScenarioHighlightFilter` (a `HighlightInfoFilter`) hides errors and warnings in that file, except undefined steps. They only come from showing a fragment: an outline without Examples, or flipped table lines that Gherkin's annotator calls "Unexpected element". Undefined steps are hidden too while an outline shows its placeholders, since those steps only match once a row fills them in. Data tables wider than the viewer are flipped into `header: value` lines, unless a line would start with a Gherkin keyword and change the parse. The text is rebuilt when the viewer is resized. Flipped keys and values get Gherkin's table header and cell colours, and each `# Row k` gets a block inlay above it: a half-line gap. The tab's padding is a border on the editor's content component, so it gets the editor's background in every theme. `ScenarioSelection` ignores the caret in the tab's own file; otherwise a click there would clear what it shows. Both tabs run or debug the target through `ScenarioRunner`, which reuses `CucumberJsRunConfigurationProducer`. The table helpers all go through `ExamplesTables`, which defines columns as the spans between `PIPE` tokens, not `GherkinTableRow.psiCells`, because an empty cell has no PSI and would shift every later column. Step data tables are left out of the table helpers on purpose. `ExamplesTables.tableOf` only accepts tables inside an Examples block.

cucumber-js behaviour, checked against 13.3.0 in `playground/js/`:
- stdout gets the **last** `--format` without a target, or `progress` if there is none. Formats from the config file and the CLI are combined, with CLI formats last.
- Feature paths on the command line are **appended to** the config's `paths`, not used instead of them. If a user's `cucumber.js` sets `paths`, a gutter run of one scenario runs the whole suite. This is a known open bug in the plugin. The playground config leaves out `paths` on purpose.
- A Scenario Outline with no Examples section still produces one pickle, with placeholders left as literal `<name>` (usually undefined steps). Examples that have only a header row produce no pickles.
- `--retry N` reports each attempt as its own `testCaseStarted`, and every attempt except the last has `willBeRetried: true`. Hook steps also count as steps in the summary.
- All `testCase` messages are emitted before the first `testCaseStarted`, also with `--parallel`. `--fail-fast` still starts every test case and reports the remaining steps as `SKIPPED`. Ambiguous steps come with no `message`. `--format message:<path>` needs a relative path; with an absolute Windows path it silently writes nothing.

Only use public IntelliJ Platform APIs. These members are `@ApiStatus.Internal` and must be avoided: `NodePackageField.getDescriptor()`, `ExecutorAction.wrap(...)`, `RunLineMarkerContributor.EXTENSION`.

## Commands

Use `./gradlew` (or `.\gradlew.bat` on Windows). CI runs on JDK 21.

- `./gradlew buildPlugin`: build the distributable ZIP into `build/distributions/`
- `./gradlew runIde`: launch a sandbox IDE with the plugin installed, opening `playground/` (debug through the IDE's `.run/runIde.run.xml` config). `playground/js/` is a Cucumber.js project covering scenario shapes and result statuses for manual testing, next to `playground/java/`. Run `npm install` in `playground/js/` first; its README maps each feature file to what it exercises. The sandbox needs an IntelliJ IDEA subscription key. `build.gradle.kts` finds the `idea.key` of an activated IntelliJ IDEA in its config directory (`IntelliJIdea<version>` under `~/.config/JetBrains`, `~/Library/Application Support/JetBrains` or `%APPDATA%\JetBrains`; the target version first, else the newest). An explicit `org.jetbrains.intellij.platform.subscriptionKey` property overrides it. Without a key, start a trial in the sandbox (Help | Register; it lives in the sandbox's config, so it's gone after the sandbox is deleted). `runIde` warns when no key is found. Without a subscription or trial the IDE runs in free mode, which disables the Ultimate-only Node.js plugin and therefore this plugin, so no gutter icons appear.
- The `runIde` sandbox also loads the Cucumber for Java plugin (the `runIdePlugin` configuration in `build.gradle.kts`, kept off the compile and test classpath). `playground/java/` is a Maven project with Cucumber for Java, for checking a mixed project (see the playground README). The `linkPlaygroundMavenProject` task, which `runIde` depends on, registers its `pom.xml` in the git-ignored `playground/.idea/misc.xml` (creating `.idea` when missing), so the sandbox imports it on opening.
- `./gradlew check`: run tests (JUnit 4 + IntelliJ Platform test framework)
- `./gradlew test --tests "com.wulfindustries.plugins.SomeTest"`: run a single test class (append `.methodName` for one method)
- `./gradlew verifyPlugin`: run the IntelliJ Plugin Verifier for compatibility checks
- `./gradlew getChangelog --unreleased`: print the unreleased section of `CHANGELOG.md`

No `src/test` directory exists yet. Put tests under `src/test/kotlin`. Platform tests usually extend `BasePlatformTestCase`.

## Architecture

- **`src/main/resources/META-INF/plugin.xml`** is the plugin manifest. Every extension (tool windows, inspections, language support, etc.) must be registered here. The `<id>` (`com.wulfindustries.plugins.better-cucumber-js`) must never change between releases. The plugin depends only on `com.intellij.modules.platform`; anything that needs JavaScript/Gherkin PSI also needs a `<depends>` entry here plus a matching `bundledPlugin(...)`/`plugin(...)` in the `intellijPlatform {}` block of `build.gradle.kts`.
- **Target IDE** is set by `intellijIdea("2026.2.3")` in `build.gradle.kts`. The README's sample version is outdated, so treat the build file as the source of truth.
- **Kotlin sources** sit directly in `src/main/kotlin/` but declare `package com.wulfindustries.plugins`. Class names referenced from `plugin.xml` (e.g. `factoryClass`) must use the package FQN, not the file path.
- **User-facing strings** go through `MyMessageBundle` (backed by `messages/MyMessageBundle.properties`, declared via `<resource-bundle>` in `plugin.xml`). Use `MyMessageBundle.message(key, ...)`, or `lazyMessage` where a `Supplier` is needed.
- **Build config**: Gradle plugin versions are pinned in `settings.gradle.kts` (`pluginManagement` plus the `org.jetbrains.intellij.platform.settings` plugin, which also sets up repositories). Library versions live in `gradle/libs.versions.toml`. Configuration cache and build cache are on in `gradle.properties`, which also holds the plugin `version`.

## Release flow

On a push to `main` and on pull requests, `.github/workflows/build.yml` builds, tests, and verifies the plugin. Only when it is run by hand (`workflow_dispatch`, Actions tab | Build | Run workflow) does it then create a draft GitHub release named after `version` in `gradle.properties`, using the `[Unreleased]` section of `CHANGELOG.md` as the notes. Publishing that draft triggers `release.yml`, which pushes the plugin to JetBrains Marketplace. That step needs the `PUBLISH_TOKEN`, `CERTIFICATE_CHAIN`, `PRIVATE_KEY`, and `PRIVATE_KEY_PASSWORD` secrets. Keep `CHANGELOG.md`'s `[Unreleased]` section current, because release notes are generated from it.

`.github/workflows/snapshot.yml` is triggered by hand (`workflow_dispatch`). It tests and builds the current commit as `<version>-SNAPSHOT-<yyyy-MM-dd-HHmm>` (UTC, passed as `-Pversion`) and creates a GitHub prerelease with that tag and the ZIP attached. Releases created with `GITHUB_TOKEN` don't trigger `release.yml`, so snapshots never reach Marketplace.
